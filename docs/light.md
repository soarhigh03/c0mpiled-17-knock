# light 구현 기록

> 2026-11-09 · `feature/light-check`

화상회의 창 **가장자리를 따라 조명판**을 달고 간헐적으로 빛을 쏴서, 그 반사광이 얼굴에
돌아오는지로 **화면 속 얼굴이 지금 이 카메라 앞에 있는 실제 표면인지**를 판정합니다.
구현하면서 측정한 것, 틀렸던 가정, 그래서 주장을 어디까지 좁혔는지를 남깁니다.

---

## 1. 지금 무엇을 주장하는가

> **"화면에 보이는 얼굴은 지금 이 화면이 비추고 있는 물리적 표면이다."**

녹화본은 다른 방 다른 시각의 빛을 입고 있고, 사진은 아예 빛을 받지 않고, 렌더된 얼굴은
모델이 정한 빛을 입고 있습니다. 세 경우 모두 이번 회차의 조명 스케줄을 따라올 수 없습니다.

| 판정 | 조건 |
|---|---|
| `pass` 1.00 | 얼굴과 주변이 **함께** 조명판을 따라감 (같은 지연으로) |
| `pass` 0.85 | 얼굴은 따라가는데 대조할 주변 영역이 없음 (뒤쪽 벽이 너무 멀어 반응이 없는 흔한 경우) |
| `pass` 0.85 | 얼굴은 따라가지만 주변과 **지연이 다름** — 경로에 뭔가 끼어 있음 |
| `fail` 0.10 | **주변은 조명판에 반응하는데 얼굴만 반응 없음** → 얼굴이 렌더되고 있음 |
| `fail` 0.15 | 밝기는 변하는데 조명판의 **색**이 아님 → 이 화면이 비추는 게 아님 |
| `fail` 0.20 | 화면 안의 아무것도 반응하지 않음 |
| `inconclusive` | 과노출 / 너무 어두움 / 주변광이 조명판을 압도 / 랜드마커가 너무 느림 / 렌더 수신증 불일치 |

**막는 것**: 영상 재생, 정지 사진, 가상 카메라로 들어오는 녹화본, 그리고 **실시간 페이스스왑** —
`sonar`가 구조적으로 못 보는 바로 그 경우 ([sonar.md §1](sonar.md#1-지금-무엇을-주장하는가)).

**못 막는 것**: 신원. light는 "이 픽셀은 실제로 빛을 받는 표면이다"까지만 말하고,
그게 **누구의** 얼굴인지는 말하지 않습니다. 그리고 조명을 충실히 재현하는 모델
([5장](#5-페이스스왑을-어디까지-잡는가)).

## 2. 신호 경로

```
서버: 세션마다 펄스 스케줄 난수 발급
      색 6개 (팔레트 7개 중 서로 다른 6개) + 시작 시각 지터 (간격 440–960ms)
  │
SDK (클라이언트)
  ├─ 송신: 창 테두리 4개 스트립 (상·하·좌·우, clamp(56px, 11vmin, 140px))
  │         펄스 사이에는 검정 — 꺼두는 게 아니라 **검정으로 켜둠**
  │         rAF 루프에서 칠하고, **다음** rAF 시각을 발광 시각으로 기록
  └─ 수신: MediaPipe Face Landmarker (sonar와 같은 face.ts 사용)
        ├─ face     = 이마 + 양 볼 패치 3개 평균 RGB
        └─ surround = 얼굴 bbox 바로 바깥 띠 3개 (벽·머리카락·어깨)
        같은 프레임에서 둘 다 — 같은 노출, 같은 화이트밸런스, 같은 순간
  │
서버 verifier
  30Hz 리샘플 → **색도**(채널/합)로 변환 → z-score
    → 채널 3개를 한 지연에 묶은 교차상관, 회전 기준선 대비
    → 펄스별 응답 (펄스 색 방향 투영, 양옆 암부 대비, 3σ)
    → face / surround 비교
```

### 2.1 왜 전체 화면이 아니라 테두리인가

**이 체크는 면접 *중에* 돌아야 합니다.** 통화 화면을 3초간 전체 색으로 덮는 제품은 없습니다.
테두리 링은 그 타협이고, 대가는 광량입니다 — 16:10 창에서 11vmin 스트립은 화면 면적의 약 1/4,
즉 전체 화면 플래시의 1/4쯤입니다. 그만큼 반사 변조는 얼굴 레벨의 몇 % 수준이 되고,
그 예산을 **지연 탐색 + 우연 기준선 대비 상관**에 씁니다. 밝기 임계값 하나로는 못 잽니다.

### 2.2 왜 간헐적인가

**암부 구간이 기준선입니다.** 각 펄스는 양옆 검정 프레임과 비교해서 채점됩니다. 그래서
"얼굴이 밝아졌다"가 가정된 주변광이 아니라 **지금 이 방 이 순간**을 기준으로 측정됩니다.
sonar도 캐리어 SNR에서 똑같은 보정이 필요했습니다 ([sonar.md §4.1](sonar.md#41-캐리어-snr을-이웃-빈과-비교한-것)).

시작 시각을 **지터**로 흘리는 건 재생 방어의 절반(나머지 절반은 색)이고, 동시에 우연 상관을
낮게 유지합니다 — 리듬 있는 자극이 우연 기준선을 0.87까지 올렸던 게 sonar의 함정이었습니다
([sonar.md §4.3](sonar.md#43-프롬프트로-1부터-10까지-세기를-시킨-것)). 부수적으로 점멸 빈도가
약 1Hz로 유지되는데, 이는 발작 위험 기준선인 3Hz보다 충분히 아래입니다 (WCAG 2.3.1).

### 2.3 왜 펄스 사이를 "투명"이 아니라 "검정"으로 두는가

투명하게 두면 암부 구간에 앱이 그리는 것(통화 타일, 컨트롤)이 그대로 들어옵니다. 그건 우리가
모델링하지 않은 광원이고, 통화 중에 변합니다. 검정으로 켜두면 테두리 영역이 **결정적**이 되고
(암부=검정, 펄스=색) 대비도 최대가 됩니다. 사용자 눈에는 "체크가 돌고 있다"는 프레임으로
보이므로 UX 손실도 아닙니다. 대신 노출 보정이 그 검정 테두리에 적응할 시간이 필요해서,
스케줄에 700ms 리드인을 둡니다.

### 2.4 왜 색인가

4장 전체가 이 질문입니다.

## 3. 측정 지표

evidence에 실려 서버가 보는 값. 모든 판정의 `reasons`에 그대로 찍히므로 실패를 사후에
진단할 수 있습니다.

| 지표 | 의미 | 시뮬레이션 | **실측 (MacBook 내장캠 1대)** |
|---|---|---|---|
| `excess` | 색도 상관 피크 − 회전 우연 기준선 | 사람 0.55–0.92, 스푸프 0.08–0.10 | 얼굴 **0.88**, 주변 0.51 |
| `chance` | 회전 기준선 자체 | 0.02–0.07 | **0.05** |
| `depth` | 펄스별 응답 / 영역 자기 레벨 | 사람 얼굴 0.85–2.8% | 얼굴 **2.96%**, 주변 0.19% |
| `n/6 pulses` | 3σ를 넘긴 펄스 수 | 사람 5–6, 스푸프 0–1 | 얼굴 **6/6**, 주변 2/6 |
| `lag` | 응답 지연 — 디스플레이 + 센서 (+ 카메라 파이프라인) | — | 얼굴 **+200ms**, 주변 +233ms ([§4.6](#46-capturetime이면-지연이-수십-ms일-것이라는-가정)) |
| `level` / `clipped` | 영역 평균 레벨과 포화 픽셀 비율 | 포화 20% 넘으면 판정 거부 | 얼굴 167 / 0%, 주변 126 / 1% |
| 렌더 정확도 | 발급 스케줄 대비 오프셋·펄스별 지터 | — | **27ms 오프셋, ±6ms 지터** (허용 120ms) |
| `clock` / fps | 프레임 클록과 실효 레이트 | — | `captureTime` / **23 fps** |
| `camera modes` | 노출·화이트밸런스 모드 (읽기만) | 대개 `continuous` | **보고 안 함** (`unknown`) |

### 첫 실측에서 확인된 것 (2026-11-09, 1대)

- **`depth 2.96%`** — 이 파일에서 "가장 중요한 숫자"라고 적어둔 `MIN_DEPTH = 0.01` 대비
  **여유 약 3배**. 시뮬레이션 추정이 2.72%였으니 광학 모델 가정도 맞았습니다. 테두리 링이
  전체 화면의 1/4 광량으로도 측정 가능한 반사를 만든다는 게 1대에서는 확인됐습니다.
- **색도 상관이 실제 하드웨어에서 분리됩니다** — 0.88 vs 우연 0.05.
- **rAF 두 번으로 찍는 발광 시각이 ±6ms** — 수신증 검사의 허용치(120ms)가 과하게 넉넉했던 게
  아니라, 부하 상황을 위한 여유로 남아 있습니다.
- 반면 `lag`와 `surround`에서 두 가지가 드러났습니다 — [§4.6](#46-capturetime이면-지연이-수십-ms일-것이라는-가정),
  [§6](#6-임계값--전부-잠정값).

아직 **1대**입니다. 사람 1명, 방 1개, 카메라 1개 — 임계값을 확정할 표본이 아닙니다.

## 4. 틀렸던 가정들

구현 중 실측/시뮬레이션으로 뒤집힌 것들. 같은 함정을 다시 밟지 않기 위해 남깁니다.

### 4.1 채널별 상관이면 "색"을 구별할 것이라는 가정

처음엔 r/g/b 각 채널을 자기 템플릿과 따로 상관시키고, "빨간 펄스에 회색 밝기 변화가 반응하면
g·b 템플릿이 예측하지 않은 응답이 생겨서 평균이 깎인다"고 생각했습니다. **아닙니다.**
팔레트가 6색이면 각 채널은 그중 3–4개 펄스에서 켜져 있습니다. 즉 **세 템플릿이 타이밍 구조를
대부분 공유**합니다. 대략 맞는 순간에 화면 전체가 밝아지면 세 채널 모두에서 동시에 점수가 납니다.

→ 1.1Hz 회색 점멸을 가진 재생 영상을 시뮬레이션하자 **그대로 통과**했습니다. 테스트가
`a client that cannot be taken at its word › is not satisfied by content that flickers on its own`
입니다.

### 4.2 평균을 빼면 밝기 변화가 지워질 것이라는 가정

4.1의 수정으로 "프레임 평균 레벨을 뺀 색차 잔차"를 쓰려 했습니다. 이것도 **부족합니다.**
피부는 붉으니 중성적인 이득 변화가 잔차를 **자기 색조 방향으로 스케일**합니다:

```
level_c = base_c · s  ⇒  level_c − mean(level) = (base_c − mean(base)) · s
```

피부 (140,105,95)에서 s를 1.00 → 1.08로 올리면 잔차가 `26.67 → 28.80`. 방향은 그대로, 크기만
커집니다. 그래서 **느린 밝기 드리프트만 있는 재생 영상에서 붉은 계열 펄스 상대로 r=0.41**이
나왔습니다. 당시 통과 임계값이 excess 0.2였으니 아슬아슬했습니다.

→ **색도**(각 채널 / 세 채널 합)로 교체. 비율은 `s`에 **정확히** 불변입니다. 램프, 상대방 화면의
밝은 슬라이드, 카메라 자체 이득 스텝, 콘텐츠 드리프트 — 전부 채널을 같이 스케일하므로
색도를 전혀 움직이지 않습니다. 같은 재생 영상의 r이 **0.41 → 0.13** (excess 0.26 → 0.08)으로
떨어졌습니다.

대가도 있습니다. 색도는 이미 작은 델타의 비율이라 노이즈가 대략 두 배가 되고, **흰색 펄스는
색도를 거의 움직이지 않습니다.** 그래서 팔레트가 *서로 다른* 6색을 뽑고, `depth`를 별도
지표로 남겨둡니다. 색도 상관은 "이 화면이 비췄는가"에만 답하고 "밝았는가"에는 답하지 않습니다.

### 4.3 깊이 비율로 페이스스왑을 잡겠다는 가정

처음엔 `face.depth × 4 ≤ surround.depth`면 스왑으로 판정했습니다. **깊이는 두 영역 사이에서
비교 가능한 양이 아닙니다** — 각 영역 자기 레벨로 나눈 값이라 **재질 항이 들어갑니다.**
같은 빛 아래에서도 어두운 중성 벽은 붉은 피부의 약 **1.9배** 깊이를 보입니다 (시뮬레이션:
얼굴 2.72% vs 주변 5.12%, 조명 이득은 5 vs 4). 임계값 4배는 그 내재 편향 위에 2배 여유밖에
남기지 않습니다 — 사용자가 화면에서 조금 멀찍이 앉기만 해도 오탐입니다.

→ **상관으로 판정**하도록 바꿨습니다. 모델은 자기 스케줄로 얼굴을 셰이딩하니 우연 수준에
떨어지고(excess 0.09), 멀리 앉은 진짜 얼굴은 여전히 조명판을 따라갑니다(excess 0.60) —
흔들림만 작습니다. 구별이 **깊이보다 상관에서 훨씬 깨끗하게** 납니다.

### 4.4 두 프레임이면 펄스 응답을 잴 수 있다는 가정

펄스 안에 프레임 2개만 있어도 표준오차를 계산했고, 그래서 **9fps 랜드마커가 통과**했습니다.
펄스당 프레임 한 쌍으로 낸 3σ는 측정이 아닙니다.

→ 펄스당 최소 3프레임을 요구하고, 그걸 만족하는 펄스가 6개 중 4개 미만이면 `inconclusive`.
동시에 홀드를 260ms → **320ms**로 늘려서 약 12fps까지는 판정에 도달하게 했습니다. 랜드마커가
프레임 레이트를 정하고(sonar 실측 23fps, CPU 추론은 더 느림) 카메라가 정하는 게 아니기 때문에
이 여유가 필요합니다. 더 늘리면 노출 보정이 펄스 안에서 플래시를 깎아낼 시간이 생깁니다.

### 4.5 통과 임계값 하나로 양쪽을 다 막으려던 것

`excess ≥ PASS_EXCESS`를 "살아있다"의 조건으로도, "우연 수준이다 → 스왑이다"의 조건으로도
썼습니다. 전자는 **높을수록** 안전하고 후자는 **낮을수록** 안전합니다. 하나로 묶으면 한쪽을
위해 올리는 모든 조정이 다른 쪽을 위험하게 만듭니다.

→ `PASS_EXCESS = 0.3` (pass의 근거)과 `CHANCE_EXCESS = 0.15` (fail의 근거)로 분리. 사이 구간은
"못 가렸다"가 정직한 답입니다.

### 4.6 `captureTime`이면 지연이 수십 ms일 것이라는 가정

`captureTime`은 프레임이 담은 순간이므로 남는 지연은 디스플레이 지연과 센서 적분 정도 —
수십 ms일 거라 보고 탐색 상한을 **250ms**로 뒀습니다. 첫 실측에서 얼굴 **+200ms**,
주변 **+233ms**가 나왔습니다. 탐색 격자(30Hz)로 한 칸 차이, 즉 **주변 피크가 천장에 붙어
있었습니다.** `SonarLab.tsx`에 이미 적어둔 말 그대로입니다 — *탐색 경계에 붙은 피크는
측정이 아니라 잘린 것.*

light에서는 sonar보다 대가가 큽니다. 두 영역이 같은 파이프라인을 공유하므로 천장보다 느린
카메라는 **양쪽을 같이** 잘라먹고, 그러면 `!face.live && !surround.live`로 내려가 `fail`이
나옵니다 — **느린 웹캠이 멀쩡한 지원자를 위조로 판정**합니다. `fail` 하나면 전체 판정이
veto되니(README 원칙 3) 이 체크가 낼 수 있는 가장 비싼 오류입니다.

→ 상한을 `captureTime` 500ms / `callback` 700ms로 넓혔습니다. 대가는 우연 기준선 상승
(시뮬레이션 0.02 → 0.07)이고 excess 0.84–0.88 앞에서는 지불 가능합니다.

200ms의 정체가 웹캠 파이프라인인지 노출 보정이 응답을 뒤로 끈 것인지는 **아직 안 가렸습니다** —
Light Lab의 `decay` 열이 그걸 보는 숫자입니다. 다만 depth 2.96%에 6/6 펄스가 응답했으므로
노출 보정이 신호를 *깎고* 있지는 않습니다.

## 5. 페이스스왑을 어디까지 잡는가

`surround` 영역이 존재하는 이유 전체가 이것입니다. 공격자는 **물리적으로 앞에 있으니** 뒤쪽 벽은
조명판을 정상적으로 반사하고, `sonar`는 "몸이 움직인다"로 통과시킵니다. 얼굴만 다시 그려집니다.

| | face excess | face depth | surround excess | 판정 |
|---|---|---|---|---|
| 사람 | 0.88 | 2.72% | 0.92 | `pass` 1.00 |
| 사람, 멀리 앉음 | 0.60 | 0.85% | 0.55 | `inconclusive` |
| 재생 영상 | 0.08 | −0.40% | −0.08 | `fail` 0.20 |
| 재생 + 자체 점멸 | 0.10 | 5.21% | −0.08 | `fail` 0.15 |
| 스왑, 조명 전사 없음 | 0.09 | 0.04% | 0.92 | `fail` 0.10 |
| 스왑, 조명 부분 전사 | 0.60 | 0.85% | 0.92 | `inconclusive` |

마지막 줄이 **열려 있는 구멍**입니다. 모델이 플래시를 색과 타이밍까지 충실히 재현한다면,
여기서는 **화면에서 멀찍이 앉은 진짜 얼굴과 구별되지 않습니다.** 두 경우가 같은 숫자를 내므로
그 구간은 `fail`이 아니라 `inconclusive`입니다 — 멀리 앉은 사람을 위조로 몰 수는 없습니다.
그리고 `inconclusive`는 light를 판정에서 빼므로, 그 세션의 판단은 sonar + environment에
얹히게 되고 **물리적으로 앞에 있는 스왑 공격자는 통과합니다.** 정직하게 적어두는 게 맞습니다.

좁힐 수 있는 길:
- **목 영역을 세 번째 ROI로.** 목은 피부(얼굴과 재질이 같아 깊이가 비교 가능)이고 얼굴 전용
  모델은 건드리지 않습니다. 턱 그림자·옷·수염·머리카락에 가려지는 게 문제라 신뢰도 게이트가
  필요합니다.
- **지연 비교를 강화.** 실시간 스왑은 50–300ms를 더합니다. 지금은 `face.live`일 때만 지연
  불일치로 점수를 깎는데(`MAX_LAG_GAP_MS`), 약한 응답에서도 지연이 쓸 만한지 재봐야 합니다.
- **공간 구조.** 지금은 영역당 숫자 하나입니다. 조명판은 테두리에 있으니 왼쪽 펄스와 오른쪽
  펄스는 얼굴에 **다른 음영 기울기**를 만들어야 합니다. 스트립을 따로 켜고 얼굴 좌/우 패치의
  차이를 보면 모델이 재현하기 훨씬 어려운 신호가 됩니다. 스키마가 ROI를 늘려야 합니다.

## 6. 임계값 — 전부 잠정값

**이 파일의 모든 수치는 시뮬레이션입니다.** 실제 카메라로 잰 게 하나도 없습니다.
sonar에서 시뮬레이션 숫자를 실측으로 착각해 겪은 일이 [sonar.md §4](sonar.md#4-틀렸던-가정들)에
남아 있습니다. 같은 실수를 하지 않기 위해 무엇을 재야 하는지 적어둡니다.

- [ ] **`MIN_DEPTH = 0.01`이 가장 중요한 숫자입니다.** 현재 설계에서 통과를 막는 건 상관이
      아니라 깊이입니다 — 조명 이득 1.5에서 excess는 0.60으로 멀쩡한데 depth 0.85%에 걸려
      `inconclusive`가 됩니다. 실제 노트북·실제 거리·실제 실내광에서 테두리 플래시가 얼굴에
      몇 %를 만드는지 Light Lab으로 재야 합니다. 1%가 흔하게 안 넘으면 링을 두껍게 하거나
      체크 자체가 밝은 환경에서 성립하지 않는다는 뜻입니다.
- [ ] **`PASS_EXCESS = 0.3` / `CHANCE_EXCESS = 0.15`** — 시뮬레이션 분리(0.10 vs 0.55)는 넓지만
      실제 r은 더 낮게 나올 것입니다.
- [ ] **`BRIGHT_SCENE_LEVEL = 200`** — 주변광이 조명판을 압도하는 지점. 이게 틀리면 밝은 방의
      멀쩡한 사용자가 `fail`을 받습니다. 가장 비싼 오류입니다.
- [ ] **`surround.live`가 자기 역할에 안 맞습니다** (첫 실측에서 드러남). surround는 두 역할을
      합니다 — ① 1.00을 위한 보강, ② **조명판이 장면을 비출 권한이 있었는지 증명**(스왑 판정의
      전제). ②에는 상관만 있으면 충분한데 지금은 `MIN_DEPTH`와 펄스 수 게이트를 함께 요구해서,
      실측에서 **excess 0.51이라는 멀쩡한 증거를 depth 0.19% 때문에 버렸습니다.**

      결과가 실제로 달라집니다. 이 셋업에 스왑이 들어오면 surround가 live가 아니니
      `the face is being rendered`가 아니라 `nothing in frame responded`로 떨어지고,
      방이 조금만 밝으면(level 200↑) **`inconclusive`가 되어 스왑이 빠져나갑니다** —
      light가 존재하는 이유인 바로 그 공격입니다. 깊이가 아니라 상관으로 판정해야 한다는
      [§4.3](#43-깊이-비율로-페이스스왑을-잡겠다는-가정)의 결론을 얼굴에만 적용하고 surround에는
      적용하지 않은 셈입니다.

      실제 스왑의 `face excess`를 재고 나서 같이 고치는 게 순서입니다 — 지금 고치면 위 실측은
      `pass 1.00`이 됩니다 (face/surround 지연 차 33ms = 격자 한 칸, 이미 일관).
- [ ] **실제 페이스스왑(DeepFaceLive 등)의 `face excess` 측정** — 모델이 플래시를 얼마나
      전사하는지가 5장의 구멍 크기를 결정합니다.
- [ ] **노출 보정 영향 측정** — Light Lab의 `decay` 열. 1보다 많이 작으면 홀드 길이나
      `exposureMode` 고정을 재검토해야 합니다.
- [ ] **`MAX_RENDER_JITTER_MS = 120`** — 부하가 걸린 머신에서 rAF가 이보다 밀리면 멀쩡한
      세션이 `inconclusive`가 됩니다. 실제 지터 분포를 봐야 합니다.

### 의도적으로 열어둔 것

- **밝은 방 → `inconclusive`는 공격자가 유도할 수 있습니다.** 화면을 아주 밝게 만든 재생
  영상을 비추면 light가 판정을 포기합니다. `fail`로 바꾸면 창가에 앉은 사람을 위조로 몰게
  되므로 이쪽이 맞습니다. 대신 aggregate의 coverage 규칙(판정된 가중치가 요청의 절반 이상)이
  "어려운 체크가 전부 inconclusive인 세션"을 막습니다.
- **`prefers-reduced-motion`을 보지 않습니다.** 보면 미디어 설정 하나로 light를 영구히
  끌 수 있게 됩니다. 대신 점멸을 ~1Hz로, 약 1/4 면적으로 유지해 WCAG 3Hz 기준 아래에 둡니다.
  접근성과 보안이 실제로 충돌하는 지점이라 적어둡니다.
- **카메라 노출·화이트밸런스를 고정하지 않습니다.** 고정하면 측정이 쉬워지지만 통화용
  스트림을 체크 편의로 재설정하는 건 우리가 할 일이 아닙니다. 모드만 읽어서 evidence에 실어
  사후 진단만 가능하게 했습니다.
- **login-demo의 mock 경로는 아직 전체 화면 색 오버레이**(`ChallengeOverlay`)입니다. 실제 SDK
  경로만 테두리 링입니다. 데모 두 경로가 달라 보이는 건 남은 정리거리입니다.

## 7. Light Lab (하드웨어 점검)

`apps/meet`의 접이식 패널. 노트북·방마다 다른 반사량을 눈으로 확인하는 도구입니다.
스케줄을 로컬에서 만들므로 **체크가 아니라 계측기**입니다 — 내가 아는 스케줄은 아무것도
증명하지 못합니다.

- **펄스별 `face Δ` / `depth`** — 비교할 때 받아 적는 숫자
- **`decay`** — 홀드 후반 응답 / 전반 응답. 1보다 많이 작으면 노출 보정이 깎고 있음
- **`clipped`** — 과노출된 영역에서 잰 응답은 의미 없음
- **`clock`** — `callback`이면 모든 지연에 카메라 파이프라인이 섞여 있음
- **`scene Δ`** — 주변 띠가 반응하는지. 얼굴만 안 반응하면 그게 스왑 신호

> Lab은 지연 보정을 하지 않습니다. 파이프라인 지연 자체가 여기서 드러나야 하는 것 중
> 하나이므로, `callback` 클록에서 Δ가 작게 나오면 없는 게 아니라 **타이밍이 안 맞은** 것일 수
> 있습니다.

## 8. 검증 방법

```bash
npm run dev          # server(:8787) + meet(:5173)
npm test -w @knock/server
```

Chrome에서 http://localhost:5173 — Safari는 `requestVideoFrameCallback`이 없어 모든 프레임이
`callback` 클록이 됩니다 (판정은 되지만 지연 탐색이 넓어집니다).

1. **카메라 켜기** → Light Lab → **빛 반사 측정** (가만히, 얼굴을 화면에 보이게)
2. `depth`가 1%를 넘는지, `decay`가 1 근처인지, `clipped`가 0%인지 확인
3. **사람 검증 시작** — 테두리가 6번 깜빡입니다 (약 6초)

스푸프 확인:
- **재생 영상**: 핸드폰으로 얼굴 영상을 재생해 카메라에 비춥니다. `얼굴 랜드마크`가 잡혀야
  측정이 성립하므로 밝기 최대로, 가까이 거치하세요.
- **페이스스왑 대용**: 본인이 앉은 상태로 얼굴 영역만 정지 이미지로 가립니다 (사진을 얼굴
  앞에 들기). 주변은 반응하고 얼굴은 반응하지 않으므로 `the face is being rendered`가 나와야
  합니다.
