# sonar (SonarGuard) 구현 기록

> 2026-11-09 · `feature/sonar-guard`

근거리 초음파 캐리어를 쏘고 그 에코로 **기기 앞에 물리적으로 움직이는 몸이 있는지** 판정합니다.
구현하면서 측정한 것, 틀렸던 가정, 그래서 주장을 어디까지 좁혔는지를 남깁니다.

---

## 1. 지금 무엇을 주장하는가

> **"이 기기 앞에 물리적으로 움직이는 몸이 있다."**

립싱크 일치(에코가 입술을 따라가는가)는 **주장하지 않습니다.** 실측 결과 CW 단일 톤으로는
불가능합니다 ([5장](#5-왜-립싱크를-포기했는가)). 립 일치가 잡히면 점수를 0.75 → 1.0으로
올리지만, 없다고 떨어뜨리지 않습니다.

| 판정 | 조건 |
|---|---|
| `pass` 1.00 | 몸이 움직임 + 에코가 입술을 따라감 |
| `pass` 0.75 | 몸이 움직임 |
| `fail` 0.10 | 에코가 정적 — 화면 속 얼굴은 움직이는데 방은 조용함 |
| `inconclusive` | 캐리어 미도달 / 랜드마커 없음 / 창 겹침 부족 |

**막는 것**: 영상 재생, AI 아바타 — 앞에 아무도 없는 경우.
**못 막는 것**: 실물이 앞에 있으면서 화면만 가짜인 경우(실시간 페이스스왑). `light`가 담당하는
영역이고, 구현됐습니다 — 주변은 조명판에 반응하는데 얼굴만 반응 없는 것으로 잡습니다
([light.md §5](light.md#5-페이스스왑을-어디까지-잡는가)).

---

## 2. 신호 경로

```
서버: 세션마다 18–20kHz 캐리어 난수 발급 (재생 공격 방지)
  │
SDK (클라이언트)
  ├─ 송신: 연속 톤, 양끝 150ms 페이드 (하드 게이팅은 클릭 → 광대역 오염)
  ├─ 수신: getUserMedia(echoCancellation/noiseSuppression/autoGainControl = false)
  │         └ 브라우저의 음향 정리 기능이 우리가 재려는 에코를 정확히 지웁니다
  └─ AudioWorklet (오디오 스레드)
        I/Q 복조 → 48:1 데시메이션(1kHz) → 6–45Hz 대역통과 → 프레임당 RMS(100Hz)
  │
  ├─ 영상: MediaPipe Face Landmarker
  │         입 벌림 = dist(13,14) / dist(10,152), 머리 = 얼굴 크기 + 중심 좌표
  │         프레임 시각은 requestVideoFrameCallback의 captureTime
  └─ 시계 정렬: AudioContext.getOutputTimestamp로 오디오 클럭 → performance.now
  │
서버 verifier
  20Hz 리샘플 → z-score → 에코 변동계수로 존재 판정
                        → (보너스) 머리 움직임 통제한 편상관, 우연 기준선 대비
```

### 대역을 6–45Hz로 자른 이유

도플러 편이는 `f_d = 2·v·f/c`. 19kHz에서 6–45Hz는 반사체 속도 0.05–0.4 m/s에 해당하고,
이게 발화 중 입술·턱이 실제로 내는 범위입니다. 아래는 정적 반사와 상체 흔들림, 위는 손동작.
처음에는 DC 위 **모든** 움직임을 담았는데, 그러면 가장 크게 움직이는 것이 측정을 가져갑니다.

### 온/오프 키잉을 쓰지 않는 이유

최초 스키마에는 `pattern` 키잉이 있었지만 뺐습니다. DC(정적 반사) 제거와 충돌하고, 게이팅
트랜지언트가 입 도플러보다 훨씬 큽니다. 재생 방지는 **세션마다 바뀌는 캐리어 주파수**가 맡습니다
— 다른 주파수로 녹음된 영상은 복조하면 잡음이 됩니다.

## 3. 측정 지표

evidence에 실려 서버가 보는 값들. 모든 판정의 `reasons`에 그대로 찍히므로 실패를 사후에
진단할 수 있습니다.

| 지표 | 의미 | 정상 범위 (실측) |
|---|---|---|
| `carrier SNR` | 톤을 켰을 때 캐리어 빈이 올라간 양 | 70–96 dB |
| `echo variation` | 대역통과 에코 RMS의 변동계수 | 사람 0.32–0.95 |
| `mouth swing` | 입 벌림 최대-최소 (얼굴 높이 대비) | 발화 중 0.06–0.12 |
| `lips: excess` | 편상관 피크 − 우연 기준선 | 보너스 판정용 |
| `doppler / mouth` | 각 시계열 샘플 수와 실효 레이트 | 100 Hz / 23 fps |

## 4. 틀렸던 가정들

구현 중 실측으로 뒤집힌 것들. 같은 함정을 다시 밟지 않기 위해 남깁니다.

### 4.1 캐리어 SNR을 이웃 빈과 비교한 것

처음엔 `캐리어 주변 9개 빈의 최대값 − 근처 빈들의 중앙값`으로 쟀습니다. **순수 잡음이어도
이 값은 4–6dB가 나옵니다** — 9개 중 최대를 고르는 순서통계량 편향입니다. 임계값을 6dB로
뒀으니 사실상 "잡음과 구별 불가" 지점에 선을 그은 셈이었고, 실제로 멀쩡한 측정이 계속
`inconclusive`로 막혔습니다.

→ **톤을 끈 상태의 같은 빈과 비교**하도록 바꿨습니다. 편향이 상쇄되고 0dB가 진짜로
"우리 톤이 아무것도 더하지 않았다"를 뜻합니다.

### 4.2 상관이 높으면 도플러일 것이라는 가정

캐리어 도달 −0.6dB(= 전혀 안 옴)인데 **소리 내어 셀 때 r=0.72**가 나왔습니다. 원인은
**치찰음**: 음성의 고주파 성분은 19kHz를 넘어 그대로 복조 대역에 들어오고, DC 제거는 변하는
성분만 남기므로 치찰음 포락선이 입 모양과 완벽히 상관됩니다. 그 상태의 sonar는 도플러가 아니라
음성 활동 탐지기였고, 녹음 재생으로 뚫립니다.

→ **대조군: 소리 없이 입모양만.** r이 0.72 → 0.27로 붕괴하면 그동안 잰 건 목소리입니다.
Sonar Lab에 `톤 순도`(캐리어 빈 vs 400Hz 떨어진 가드 밴드)를 같이 띄워서 순음인지 광대역인지
바로 보이게 했습니다.

### 4.3 프롬프트로 "1부터 10까지 세기"를 시킨 것

숫자 세기는 **가능한 자극 중 가장 주기적**입니다. 리듬 있는 입은 리듬 있는 에코와 아무 지연에서나
맞아떨어져서, 한쪽 시계열을 회전시켜 정렬만 깨뜨린 우연 기준선이 **0.87**까지 올라갔습니다
(진짜 신호 r=0.91 대비). 상관 수치 자체가 정보를 거의 안 담고 있었습니다.

→ 자극을 **추가**하는 게 아니라 **빼서** 해결했습니다. 면접에서 오가는 자연스러운 말은 불규칙한
쉼과 변하는 속도가 있어서 우연 기준선이 0.11로 떨어집니다. 제품 요구사항(면접을 방해하지 않는다)과
신호 품질이 같은 방향을 가리킨 경우입니다.

### 4.4 영상 프레임을 콜백 시각으로 찍은 것

`requestVideoFrameCallback`의 `now`는 콜백이 **실행된** 시각이고, 프레임이 담은 순간보다 카메라
파이프라인만큼(100–200ms) 뒤입니다. 그래서 에코가 입술보다 **앞서는** 음수 지연이 계속 나왔습니다.
→ `metadata.captureTime`으로 교체.

### 4.5 `inconclusive`를 0.5점으로 평균에 섞은 것

미구현 상태인 `light`가 0.5점으로 가중 평균에 들어가 멀쩡한 세션을 0.6965까지 끌어내렸습니다
(임계값 0.7). "못 쟀다"를 "절반쯤 가짜"로 취급한 셈입니다.

→ 판정에 도달한 체크만 평균에 넣되, **판정된 가중치가 요청한 것의 절반 이상**이어야 통과하도록
했습니다. 어려운 체크가 전부 inconclusive일 때 약한 체크 하나로 통과하는 걸 막습니다.

## 5. 왜 립싱크를 포기했는가

캐리어가 정상 도달(70dB+)하고 자연스러운 말을 해도 사람과 가짜가 갈리지 않았습니다.

| | excess | echo variation |
|---|---|---|
| 사람, 경직 상태 | 0.22 (통과) | 0.37 |
| 사람, 자연스럽게 움직임 | −0.04 (실패) | 0.95 |

**고개를 끄덕이는 것만으로 무너집니다.** 머리는 입술보다 훨씬 큰 반사체고, 에코는 프레임당
숫자 하나라 둘을 분리할 수단이 없습니다.

영상으로 머리 움직임을 재서 통제변수로 넣는 **편상관**을 시도했고, A/B로 효과를 쟀습니다
(머리 반사를 입술 대비로 키우며):

| 머리/입술 반사비 | 편상관 | 통제 없음 |
|---|---|---|
| 0× | 0.67 pass | 0.67 pass |
| 1× | 0.53 pass | 0.47 pass |
| 2.5× | **0.16 pass** | −0.01 fail |
| 5× | −0.03 fail | −0.02 fail |
| 12× | −0.05 fail | −0.03 fail |

작동 범위가 2.5배까지 늘었지만 그 이상은 못 건집니다. **에코 에너지는 복소수 합의 크기**라서,
큰 반사체가 지배하면 작은 쪽이 변동하는 위상에 섞여 흩어지고 선형 회귀로는 되돌릴 수 없습니다.
크기를 취하기 **전에** 분리해야 합니다.

### 올라갈 길: FMCW

처프로 거리 분해능을 얻으면 됩니다. 18–22kHz(B=4kHz)면 `Δr = c/2B ≈ 4cm`로, 얼굴과 상체·손·배경을
거리 빈으로 분리하고 머리 벌크 움직임을 복소수 영역에서 보상할 수 있습니다. 워클릿 복조부
재작성 + 스키마에 거리-도플러 맵 + verifier 재작성이 필요합니다.

## 6. Sonar Lab (하드웨어 점검)

`apps/meet`의 접이식 패널. 노트북마다 다른 18kHz 이상 응답을 눈으로 확인하는 도구입니다.

- **주파수 스윕** — 17.5–22kHz를 500Hz 간격으로, 각 주파수마다 톤 on/off를 3회 번갈아 측정해
  드리프트를 상쇄. 룸 노이즈(`±` 열)를 같이 보고해서 못 믿을 측정이 못 믿게 보이도록 했습니다.
  고주파에서 아무것도 안 잡히면 그때만 가청 대역(14–17kHz)까지 내려갑니다 — 귀가 아프므로.
- **실시간 그래프** — 도플러 에너지(파랑) vs 입 벌림(분홍)
- **캐리어 도달 / 톤 순도 / 상관 중앙값**

> 한 번은 전 대역이 0dB 근처로 나왔는데 원인이 **시스템 음량**이었습니다. 음량을 올리니
> 17.5–22kHz 전 대역 23–35dB. 스윕이 없었으면 한참 더 헤맸을 겁니다.

## 7. 남은 일

- [ ] **실제 스푸프의 `echo variation` 측정** — 지금 임계값 `MIN_PRESENCE_VARIATION = 0.2`는
      사람 실측(0.32–0.95)과 **시뮬레이션** 빈 방(0.11) 사이에 둔 잠정값입니다. 사람이 화면 밖으로
      완전히 빠진 상태의 재생 영상을 측정해서 확정해야 합니다. 실측 최저값이 0.32라 여유가 넓지 않습니다.
- [x] **`sonar` 가중치 재검토** — 0.4 → 0.35, `light`도 0.3 → 0.35. 주장이 "몸이 있다"로
      좁아졌고 페이스스왑은 아예 못 보는 반면, light는 화면 속 얼굴이 실제 표면인지에 유일하게
      답합니다. 동등한 가중치가 맞습니다. `light`가 구현되기 전에는 내릴 수 없었습니다.
- [ ] **`PASS_EXCESS = 0.15`** — 보너스 판정 임계값. 시뮬레이션 기준 잠정값.
- [ ] 노트북별 스윕 결과 수집 → 서버 캐리어 범위(18–20kHz) 재조정
- [ ] 통화 중 송출 오디오에서 캐리어 노치 필터링 (상대방에게 우리 톤이 넘어감)
- [ ] FMCW 전환 여부 결정

## 8. 검증 방법

```bash
npm run dev          # server(:8787) + meet(:5173)
```

Chrome에서 http://localhost:5173 — Safari는 `requestVideoFrameCallback`이 없어 입 시계열이 비고
항상 `inconclusive`가 됩니다.

1. **스피커로 소리가 나야 합니다.** 이어폰을 꽂으면 스피커→방→마이크 경로가 사라집니다.
   시스템 음량도 올려야 합니다.
2. Sonar Lab → **주파수 스윕** (가만히, 조용히 15초)
3. **사람 검증 시작** → 평소처럼 15초 말하기. 아무것도 요구하지 않으므로 자연스럽게 행동하면 됩니다.

스푸프 확인: 핸드폰으로 말하는 영상을 음소거 재생해 카메라에 비추고, **본인은 화면 밖으로 완전히
빠져서** (손도 안 보이게 거치) 돌립니다. `입 벌림`이 0 fps면 영상 속 얼굴을 인식 못 한 것이라
측정 자체가 무효입니다 — 핸드폰을 더 가까이, 밝기 최대로.
